# Scaffold: fondamenta del progetto

Prepara il terreno perché il loop possa correre: skeleton, test harness, contesto.

## Procedura

1. **Stack.** Leggi `architecture.yaml`, le fonti `blueprint/` e `DESIGN/` in sola lettura, poi `profiles/<profilo>/stack.md`. Se il PRD ha vincoli che contraddicono il profilo vince il contratto approvato (annotalo in `CONTEXT.md`); se il tipo di progetto non è coperto scegli lo stack più standard e annotalo come decisione. Registra in `project.yaml → skills:` le skill tecnologiche effettivamente usate.
2. **Skeleton** che si avvia con un comando, dal PRIMO COMMIT:
   - per una soluzione full-stack `frontend/` e `backend/` sono radici distinte; `DESIGN/` non diventa il codice di produzione;
   - con una UI, il tema nasce dai token di `design_language` in un unico file e la shell (layout, navigazione) è il primo componente, senza valori visivi hardcoded nei componenti (skill `design-implement`);
   - test runner configurato con almeno 1 test verde, lint e formattazione, script `dev`, `test` e `build`, `.env.example` se servono segreti (mai segreti veri nel repo);
   - ambiente eseguibile dentro il progetto: per Python un `.venv` con il test runner installato, per Node le dipendenze locali. Il runner attiva da solo `.venv` e `node_modules/.bin`;
   - validazione della specifica OpenAPI e client tipizzato del frontend generato o verificato: i tipi di rete non si copiano a mano tra le due radici;
   - per ogni prodotto con API HTTP (`protocol: http` in `blueprint/api.yaml`), contract test con lo strumento che lo stack offre: ogni risposta reale delle prove (status e corpo, mai un mock) è validata contro lo schema della specifica, così un campo rinominato o un tipo cambiato è rosso;
   - un test confronta le rotte registrate dal server con le path della specifica: una rotta in più (un endpoint che nessuno ha dichiarato, magari con dati personali) è rossa dal primo commit; una rotta della specifica che manca diventa rossa quando il task che la costruisce è chiuso, perché quel task la aggiunge alle rotte attese del test. Dove il framework non elenca le rotte il confronto copre solo quelle della specifica, e la rotta in più non si vede;
   - su un backend già avviato preserva codice, manifesti e migrazioni: aggiungi solo `frontend/`, contratto, wiring e test.
3. **Database**, se `blueprint/database.yaml` ne dichiara uno, configurato e FUNZIONANTE dal primo commit: connessione solo via `DATABASE_URL` letta da `.env`; migrazioni inizializzate (Alembic, Prisma o equivalente: lo schema nasce migrato, mai `create_all` sparsi); un comando unico che prepara il DB di sviluppo (lo crea se manca, applica le migrazioni, seed minimo) e un avvio che fallisce con un messaggio chiaro se le tabelle mancano; un test REALE di connessione senza mock (DB temporaneo, tutte le migrazioni, un giro insert e select), coerente con i comandi `verification` del contratto database. Con PostgreSQL il ruolo di `DATABASE_URL` è `NOSUPERUSER NOCREATEROLE`, proprietario del proprio schema e senza membership in `pg_execute_server_program`, `pg_read_server_files` o `pg_write_server_files`: le migrazioni DDL ordinarie restano sue, ma non esegue programmi del server né legge o scrive file del server. Il bootstrap amministrativo usa `DATABASE_BOOTSTRAP_URL` solo in `.env.local` radice, mai in `.env`, `project.yaml env` e non negli `env_files` globali: un figlio bootstrap invocato da `lifecycle.setup` legge il file con il parser del progetto, passa la credenziale solo al suo comando amministrativo e termina. Prima di creare `.env.local` o inserire valori bootstrap esegui `git check-ignore -q -- .env.local`; se non è ignorato o è già tracciato, fermati, registra la domanda in `QUESTIONS.md` e chiedi un aggiornamento esplicito di `.gitignore`. Non scrivere credenziali, non aggiornare automaticamente `.gitignore` e non mutare altri file legacy. `lifecycle.start`, healthcheck, connessioni e suite non ricevono bootstrap; non serve un unset nell'app per un segreto che non è nel parent.
4. **Contratto operativo.** Aggiorna le fonti Blueprint quando l'implementazione rende concreta una scelta astratta e ricompila; i formati sono in `docs/BLUEPRINT.md` (fonti) e `docs/ARCHITECTURE-YAML.md` (`architecture.yaml`) della casa Factory, la cartella sopra `bin/` del comando `factory`: leggili, non leggere il sorgente del runner; poi completa `architecture.yaml` con i comandi reali di setup, start non bloccante, stop, healthcheck, environment (solo riferimenti ai segreti), connessioni, suite, `data.migrations` e `data.seed`, e l'infrastruttura applicabile. Porta `status: ready` quando `factory architecture validate . --ready` è verde e lo stack si avvia con i comandi della ricetta (setup, start, salute, connessioni, migrazioni, seed); `factory architecture test .` e le journey dei flussi non si lanciano qui: diventano verdi con i task e le esegue il Macro Contract finale. Per un frontend configura Playwright contro il `baseURL` reale e dichiara una `journey` per ogni spec (`playwright-e2e`). `factory architecture update .` modifica il contratto con il wizard.
   - **Ricetta dell'ambiente, non CONTEXT.md.** I comandi `install`, `build`, `test`, `e2e` e `start` degli ambienti `development` e `test`, e in `tools` i programmi necessari, stanno in `blueprint/deployment.yaml` (schema 3): `derived` solo se un file del progetto lo prova (da citare in `evidence`), `convention` per il comando usuale dello stack, `not_found` senza comando se non esiste; mai valori inventati. Se il file è ancora di schema 2 passa a 3. Dopo averlo scritto ricompila.
   - **`data.migrations` e `data.seed` sono comandi, non percorsi**: il collaudo li esegue dopo `start`, a healthcheck verde, e devono poter girare anche una seconda volta (`cd backend && npx prisma migrate deploy`, mai `backend/prisma/migrations`, che fallisce con `is a directory`). `data.backup` e `data.restore` sono descrizioni che il runner non esegue.
   - `lifecycle.setup`, `start` e `stop` devono poter girare più volte di seguito con lo stesso esito: il kernel li rilancia a ogni collaudo e `stop` gira anche dopo un setup o uno start falliti. Niente comandi che falliscono se il risultato c'è già (`mkdir` senza `-p`, `ln -s` senza `-f`, `createdb` o `CREATE ROLE` senza controllo, migrazioni non rieseguibili) e niente comandi che cambiano lo stato a ogni giro (append a file con `>>`, seed che duplica righe). Giusto: `test -f docker/.env || cp docker/.env.example docker/.env`. Sbagliato: `cp -n docker/.env.example docker/.env`, che su macOS esce con 1 se il file c'è già. Il bootstrap del database crea ruolo e database solo se mancano.
   - **`lifecycle.start` e i comandi del collaudo umano avviano il codice corrente**, mai una build lasciata da un avvio precedente: ricompila prima di partire, e se uno stack è già acceso fermalo o rifiutati con un messaggio chiaro. Altrimenti l'interfaccia chiama operazioni che il server vecchio non ha (404) e i verify dei task, che girano sul sorgente, restano verdi. Prova: cambia un file del server, rilancia solo l'avvio e controlla che il cambiamento si veda.
   - **I servizi che il progetto usa (database, posta, code) li accende il collaudo da sé**: con un compose di sviluppo del progetto lanciato da `lifecycle.setup` o `start` (non quello di `infra/` per il rilascio), oppure con un servizio nella ricetta, con una porta sua. Mai un prerequisito `check: manual` per il collaudo: un servizio acceso a mano o rimasto da un giro precedente fa passare il collaudo per il motivo sbagliato.
   - La suite di sistema parte da dati di prova azzerati nel setup. Le journey girano nell'ordine dei file sullo stesso database e creano dati con nomi fissi (utente, cliente, riferimento dell'ordine): se i dati di un giro restano, il giro dopo li trova già lì e riceve un rifiuto «esiste già» che la fixture rende rosso. Il database dell'ambiente di prova, mai quello di sviluppo, riparte vuoto prima di migrare e seminare: con SQLite si rimuove il file indicato dal suo `DATABASE_URL` (`rm -f` esce 0 anche se manca), con un server si ricrea lo schema di prova, oppure si fa `docker compose down -v` nello `stop`. Lo si dichiara in `lifecycle.reset`: il kernel lo esegue dopo `setup` e prima di migrazioni, seed e `start` ogni volta che il collaudo lancia la suite di sistema o le journey (passo «reset dei dati»), quando nessun server tiene aperto il file; senza `reset` i dati di un collaudo restano al successivo. Il comando resta ripetibile: stesso stato finale a ogni lancio.
   - **L'healthcheck può guardare anche il corpo.** Oltre a `http` (il solo codice) e `tcp` (la sola porta) esiste il tipo `command`, che passa se il comando esce 0: per esempio un `curl` con un `grep -q` sul contenuto dello stato di salute, per accorgersi di un servizio che risponde 200 anche quando sta male.
   - Con un Dockerfile il servizio ascolta su tutte le interfacce (`0.0.0.0`), non solo su `127.0.0.1`: dall'esterno del contenitore altrimenti non si raggiunge, e un healthcheck sull'host non se ne accorge.
   - Gli script lanciati come comando devono essere eseguibili (`chmod +x`, `100755` in Git) o lanciati con il loro interprete; pid e log dell'avvio stanno fuori dal progetto o in una cartella ignorata da Git, perché `start-contract`, `integrate-contract` e `promote-dev` rifiutano un albero sporco.
5. **CONTEXT.md**: la mappa per un agente che non ha mai visto il progetto: albero delle cartelle con una riga ciascuna; una riga su come l'avvio ricompila e dove stanno pid e log (i comandi stanno nella ricetta); l'ingresso di sviluppo e l'account di prova se l'accesso arriva in un blocco dopo quello di una journey (`playwright-e2e`); convenzioni attive del profilo; dove si aggiunge cosa; dove vivono i design token (`design_ref` e `design-implement`), il contratto OpenAPI, la connessione al DB e come si aggiunge una migrazione; decisioni prese e perché.
6. **Chiudi.** Esegui `factory blueprint validate . --ready`, `factory architecture validate . --ready`, test e build, poi committa. Fermati: lo stato del task di scaffold e la firma del piano non sono tuoi, li registra la persona con `factory approve-plan` (o l'app). Non eseguire quel comando.

## Regole

- Il test harness non è opzionale: senza, il loop non ha gate di verifica.
- Meno dipendenze possibile: ogni libreria in più è manutenzione per sempre. Lo skeleton è noioso e standard, la creatività va nelle funzionalità.
- Lo scaffold è lo scheletro, non il prodotto: oltre alla salute e alla shell, nessuna rotta, vista, calcolo, validazione o formato delle funzionalità del piano. Ciò che un Task Contract dichiara lo costruisce il suo task, con il suo verify e la sua review.
- CONTEXT.md è scritto per chi non ricorda: se un'informazione serve per lavorare, sta lì, non nella tua memoria.

## Review di sistema con database

Se `blueprint/database.yaml` dichiara schema, migration e integration test, lo scaffold genera `scripts/review.sh`: riceve il comando di review già scelto dalla suite, non avvia servizi o un secondo stack, esegue i tre comandi di verifica dichiarati dal contratto dopo setup, dati, health e connessioni, poi conserva argv e codice d'uscita con `exec`. Esempio Node da sostituire con i tre comandi ESATTI del contratto dello stack:

```sh
#!/bin/sh
set -eu
[ "$#" -gt 0 ] || { printf '%s\n' 'Manca il comando di review.' >&2; exit 2; }
npm --prefix backend run test:db:schema
npm --prefix backend run test:db:migration
npm --prefix backend run test:db:integration
exec "$@"
```

Il wrapper non cambia la cartella corrente per i comandi che riceve in coda: `--config`, gli spec relativi come `tests/system-e2e/...` e `--reporter` che il kernel aggiunge sono scritti rispetto alla radice del progetto, e un `cd backend` prima di `exec "$@"` fa partire Playwright da `backend/`, dove non trova né config né spec, ed esce con errore senza report (a fallire sono sia il collaudo completo sia il controllo degli status di fine blocco). I passi che servono in una sottocartella si fanno con l'opzione della propria CLI, come `npm --prefix backend` dell'esempio o `python -m pytest backend/...`, oppure in una subshell `(cd backend && ...)`.

`testing.review_suite` resta il nome della suite; cambia `testing.suites.<nome>.command` al wrapper. Con frontend, per esempio, il comando della suite diventa `sh scripts/review.sh npx playwright test --config playwright.system.config.ts` (in un progetto adottato `--config .factory/system-e2e/playwright.system.config.mjs`, skill `playwright-e2e`); gli spec aggiunti dal runner restano negli argv. Un backend-only passa al wrapper il suo comando di review reale, senza inventare Playwright. I comandi DB non diventano verify nudi del Task o del Macro Contract prima del lifecycle e `database_impact.required` resta riservato all'impatto DB reale.

Questa ricetta e la promessa delle tre verifiche DB valgono solo per la review standard. Se `testing.independent_test.enabled: true`, il percorso trusted non usa `testing.suites.<nome>.command`: non dichiarare il wrapper come prova che schema, migration e integration test siano eseguiti dal Test indipendente, e non disattivare o modificare il Test indipendente per applicare la ricetta standard.
